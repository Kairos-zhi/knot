## 零、2026-11-15阶段澄清：当前解释以本节为准

用户明确指出，下述场景属于**第二个MVP**：“你用 Codex 开发 Knot。做完后，插件帮你整理：今天完成了什么、卡在哪里、下次接着做什么。你检查一下，再决定是否同步给团队。”此前助手将它解释为最初目标，范围判断有误。

| 阶段 | 要让用户做到什么 | 如何判断成立 |
|---|---|---|
| 第一个MVP：自由探索 | 在实际使用的 Codex 中取用已有材料，选择/排除/重新组合，表达或改变关系，比较方向、另开思路，保留问题、暂定判断、否决与未决，回来继续 | 用户自主提出非预设问题，改变材料、关系或方向，形成可继续使用的思考与产物；来源、输入边界、反馈及恢复清楚 |
| 第二个MVP：工作上下文整理与团队同步 | 从 Agent 工作过程整理项目/任务进展、阻塞、下一步及阶段成果，由用户检查，再决定是否向团队同步 | 整理内容及其来源可检查，项目/任务目标准确，用户确认范围明确；只有真实接收回执才能称同步完成 |

第一个MVP沿用先前明确的五组能力：**取用材料、选择与关联、展开与转向、留下并继续、理解操作后果。** 插件是接入方式，项目分类、记事、进度总结或固定续接包均不能单独替代这一目标。原始目标回溯见[《KNOT插件开发重点》](https://chatgpt.com/c/6ae8c9a1-b60c-83ee-9011-0f0b3cb2ae00)；实际用户在该讨论中要求先做到能够自由探索，并通过使用判断剩余价值。

本轮对原卡的处理：

- 原A/B/C中的材料归属、草稿隔离和连续界面可以作为支撑候选，但完整项目/任务管理不自动成为第一个MVP的前置条件；须按自由探索实际缺口重新裁切。
- 原D的任务进展整理、证据检查和导出属于第二个MVP的相关基础候选。本机导出不等于团队同步，宿主工作上下文的实际提取和团队接收也尚未由原D覆盖。
- 不再按原A → B → C → D直接推进或据此判断第一个MVP完成。当前主线应先核对五组探索能力在实际 Codex 中的可用性，再固定最小工程切片；本次澄清不宣称已经完成该对账。
- 第二个MVP保留为明确的后续目标，不删掉，也不作为第一个MVP已实现能力或完成门槛。两阶段的技术检查、人的体验和完成结论分别记录。

**以下第一至九节保留2026-11-14原方案供追溯，不是重新批准的实施顺序。原文中的“本阶段”“第一阶段”不再解释为第一个MVP的正式范围；与本节冲突时以本节及用户本次澄清为准。**

## 一、问题与目标

当前页面围绕“继续思考、找材料、写想法”组织，尚未围绕项目、任务及其连续工作组织。暖橙、侧栏和折叠详情已落地，但用户仍难以回答：我正在推进哪件事，上次到哪里，现在会把哪些内容留给哪个任务。

本卡目标：让用户进入一个真实登记的本地项目，找到具体任务，在同一个工作现场阅读材料、继续草稿、检查阶段整理结果，并分清草稿留存、版本保存、本机导出和平台接收。

最小验收路径：**进入 Knot 项目 → 找到插件接入任务 → 回到上次材料与记录 → 边读边补充 → 切到另一项目再返回 → 检查并确认保存 → 检查任务上下文并明确导出。**

## 二、设计预期与当前差距

| 维度 | 设计预期 | 基线实际情况 | 本卡处理 |
|---|---|---|---|
| 工作组织 | 项目、任务和工作现场有稳定身份 | 保存记录平铺，导航按操作分类 | 先建立项目/任务及显式关联，再组织导航 |
| 多项目 | 各现场分别保留草稿、选材和进展 | 全页只有一个当前草稿 | 按当前身份与任务隔离、持久化和恢复 |
| 连续工作 | 阅读和写作围绕同一任务持续进行 | 阅读与写作切换区域；未准备草稿刷新会丢失 | 同一工作区承接阅读、草稿和已选材料 |
| 插件作用 | 来源、任务状态和阶段整理结果可检查 | 来源固定到保存版本；状态与摘要手填，仅本机导出 | 将已有能力接入任务主流程，明确手填与实际来源 |
| 材料使用 | 预览与采用分开，目标始终清楚 | 已有显式采用/导出边界，缺少业务归属 | 保留边界，补任务目标与关联校验 |
| 成果与复用 | 结果有身份、来源，可再次引用 | 已有版本和材料引用，尚无成果库闭环 | 本卡呈现版本与来源；成果验收/模块化另卡 |
| 视觉 | 克制、焦点明确、真实状态可见 | 已有基础样式，不能据此认定体验达标 | 围绕真实对象重排，按连续任务进行人的验收 |

UX-001 的86项 Maker 检查和限定 Gate 是该卡历史证据，不证明本卡的项目对象、草稿恢复、宿主任务识别或平台同步已经实现。

## 三、范围与边界

本阶段先支持一个操作者在本地明确创建项目、任务并关联已有材料或保存版本。项目可用真实名称显示，但名称来自显式登记；不从目录名、聊天或探索 ID 猜归属。旧记录默认进入“未归入项目”，由用户明确关联，保留原记录身份和历史。

同一材料可以被不同任务明确引用；项目分组本身不授予读取、交给 Agent、导出或公开的权限。项目/任务对象由共享服务维护，界面和宿主适配器复用同一业务语义，不能只在浏览器另存一套项目事实。

本卡不包含自动扫描所有工作目录、自动识别多项目、自动能力推断、真实模型运行、平台账号绑定及上传。第一阶段的任务状态和摘要仍由操作者填写并标明来源。Agent 未接入时直接显示“未连接 Agent”；本机包不能显示“已同步平台”。自动提取须另行固定一个实际宿主、输入范围和授权方式后拆卡。

不恢复旧桌面应用，不同时建设文件系统、空间画布、浮窗和工作岛。现有资产、探索版本、保存恢复与上下文包继续复用；已有协议不得因界面重排而静默改变。

## 四、对象与状态约定

以下是子卡 A 须正式固定的最小语义，不等于已新增数据库表或接口。

| 对象 | 最小要求 |
|---|---|
| 项目 | 稳定本地身份、显示名称、当前操作者归属；与其他本地范围及平台项目明确区分 |
| 任务 | 稳定身份、所属项目、目标、操作者报告的进度；进度不自动等同验收结果 |
| 工作现场 | 引用一个任务及其当前材料、工作记录和草稿；阅读焦点与写入目标分别保存 |
| 探索保存版本 | 继续使用原 exploration/revision/event 身份；与任务显式关联，历史不改写 |
| 任务草稿 | 绑定当前身份、本地范围与任务；含文字、选材、关系及基于哪个版本编辑；独立留存与恢复 |
| 上下文包 | 目标绑定具体项目/任务和固定来源版本，状态、摘要、允许导出的证据分别检查 |

任务创建和更名、关联/解除关联、草稿留存/恢复、版本准备/确认均应有清楚的操作结果。子卡 A 固定最小字段、接口输入输出、权限、错误、版本冲突、重复请求及失败恢复规则，再进入持久化实现。

保留现有上下文协议的 `namespace_id/project_id/task_id` 语义。新增本地登记不能冒充平台登记，也不能将 `user_assigned_unverified` 静默升级为平台已验证。旧包保留其版本和语义；需要变更协议时显式版本化。

草稿留存与正式保存分开反馈。界面只在持久化成功后显示“草稿已留在本机”；失败时保留可编辑内容并告知未留存。恢复只读取当前身份和当前任务的草稿，不自动发送、导出或生成新正式版本。内容读取仍需重新验证授权与哈希，不把草稿缓存作为绕过不可用材料的通道。

现有保存入口最多有一笔 prepared/unknown 待处理操作，不能通过增加多份草稿假装已有并发保存。第一版可保留单笔待处理限制，但操作必须绑定原任务与原请求；切换任务不清空、不重绑，不允许借新任务重发。UI应能明确返回原任务处理；unknown 继续只允许显式检查/恢复原请求。

## 五、界面要求

| 区域 | 默认呈现 | 关键行为 |
|---|---|---|
| 项目导航 | 已登记项目及其任务；另列未归属记录 | 使用人可读名称；切换恢复各自现场，不自动采用所预览材料 |
| 当前任务顶部 | 项目/任务名、目标、进度及其来源、真实保存状态 | 始终能回答当前写入目标；阅读别处材料不改变它 |
| 主工作区 | 当前材料正文、来源摘要、阶段记录与草稿 | 宽屏允许并排，窄屏可顺序展开；保持同一任务身份和草稿，不靠页面跳转重新找内容 |
| 本次使用材料 | 已明确采用的材料、采用/排除状态 | 可检查和移除；预览不默认加入，跨任务引用须明确操作 |
| 上下文检查 | 目标任务、来源版本、手填状态/摘要、允许导出的证据 | 改目标或内容即使旧预览和确认失效；完整预览和导出确认均保留 |
| 结果反馈 | 草稿留存、版本保存、本机导出各自结果 | 无平台回执时显示“未连接平台”或“仅本机导出”；失败和结果未知有可执行下一步 |

沿用暖橙与中性灰、单一主要强调、清楚焦点和渐进披露。编号、哈希、字节偏移和原始校验信息默认折叠；任务名称、来源概况、授权范围、失败及恢复动作不藏在高级详情中。中文长文、键盘路径、缩放、窄屏、深色及减少动态效果各有检查项。

## 六、实施拆分与顺序

| 子卡 | 核心交付 | 完成条件与依赖 |
|---|---|---|
| UX-002A｜项目、任务与现场契约 | 核已有实现及成熟机制；固定对象关系、身份边界、操作/错误契约、旧记录关联、草稿持久化和恢复规则 | 契约示例覆盖双项目、跨身份、旧版本及未知保存；独立定义复核通过后 B 开工 |
| UX-002B｜本地归属与独立草稿 | 共享服务中的项目/任务登记与关联；草稿留存/恢复；保存操作归属和冲突保护 | 使用合成临时库验证；重启仍能分别恢复，无越权、串写或未知请求重复发送；不迁移用户在用库 |
| UX-002C｜连续工作界面 | 以 B 的真实对象组织导航、任务工作区、阅读/写作、已选材料与恢复提示 | B 的对象/操作已可用；完成双项目连续路径；无伪目录、伪执行状态；程序化检查通过后交用户体验 |
| UX-002D｜任务上下文检查与本机导出 | 任务目标关联已保存来源，检查进度、摘要和允许导出的证据，完整预览并明确导出 | 依赖 A/B/C；沿用私有导出保护与协议边界；目标不匹配拒绝，不误报平台接收 |

## 七、验收路径

使用显式标记的两组合成项目与任务：A 为 Knot／插件接入，B 为研究／材料整理。它们具有不同任务身份、文字标记与材料引用；不能以硬编码展示替代真实登记、保存和读回。

1. 进入 A，能辨认任务目标、当前材料、上次正式记录、草稿状态，以及 Agent/平台是否连接。
2. 阅读一份材料，不自动加入任何任务；明确加入 A 后，只改变 A 的选材。
3. 在 A 写草稿，切到 B 写另一份，再返回 A；文字、选材、来源版本及阅读位置分别保留。
4. 确认草稿已留存在本机后刷新或重启；可分别恢复 A/B。持久化失败时不显示成功，也不丢弃仍可保留的编辑内容。
5. 保存 A 前能核对其文字、材料、目标及基于的版本；独立确认后才产生正式保存。旧版本保留，冲突不覆盖。
6. 故意制造 A 的保存结果未知，再切到 B；待处理操作仍归 A，不能以 B 的目标或新请求替换它。显式恢复只重用原请求，不能新增重复版本。
7. 再次读取材料遭拒绝或内容变化后，正文和各处由正文得出的名称不残留为可用信息；草稿、搜索和旧记录入口同步反馈，不自动重试或补回材料。
8. 从 A 的已保存版本整理上下文，只导出明确允许的 A 证据与主动摘要，不混入 B 的草稿或默认选材；改目标/来源后旧确认失效，误配拒绝。
9. 导出完成只显示本机导出结果。没有平台认证、接收接口和可核验回执时，始终不显示“平台已接收”。

人的体验验收单独进行：无需开发者解释，能回答“我在哪个项目做什么”“上次到哪里”“这次采用哪些材料”“这些内容目前保存或发送到哪里”，并能完成上述连续操作。无法回答时回到结构与语义调整，不以测试数、配色或按钮存在抵消。
