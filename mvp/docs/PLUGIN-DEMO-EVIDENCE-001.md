# PLUGIN-DEMO-EVIDENCE-001｜为一条真实需求生成项目证据卡

2026-11-18 · 本地 Demo 已实现 · 开发基线 `ba80b73`

## 要证明什么

让一位没看过开发者原始对话的需求方，在一分钟内看懂三件事：这位开发者做过哪件和需求有关的事、去哪里核对、还有哪项能力或条件需要确认。

这是商业化 Demo 的插件部分。个人工作台为需求匹配和交付提供证据。本卡交付「一条需求 → 一个已有项目 → 一张可核对的候选证据卡」。平台邀约、承接确认和后续交付动态分别接续。

## 演示入口与交付

1. **为这条需求生成项目证据。** 在现有项目页填一条需求的标题、预期交付物和验收要求。需求方原话可保留为输入。已有平台任务编号可填，编号缺失时按本地需求展示。
2. **从项目里选证据。** 复用项目回顾和材料读取。插件用选中的可读材料准备整理指令，开发者可沿现有「复制指令 → 粘贴结果」流程生成草稿，也可手动填写。卡片按需求条目列最多三项证据，每项回答「我做了什么」「对应哪项要求」「如何核对」。有来源但个人贡献不明确时标「本人贡献待核」，找不到对应证据时保留缺口。
3. **核对后生成分享卡。** 开发者核对本人贡献，在接收者预览中逐项选择可共享的摘录和成品链接，默认不选。至少勾选一段可追溯到原文的摘录后，即可复制一页 Markdown 到候选页。成品链接由开发者提供，并核对访问权限。

卡片内容依次为**需求、本人做过的相关工作、核对方式、待确认项**。核对区可打开完整本地来源。接收者只看本次批准的字段；本机文件与私有对话用核准摘录或可对外访问的链接支撑，只有本机可读的来源明确标注。

## 实现落点

- 复用 `mvp/devtools/project_review.py` 的指令与回填方式，以及 `workbench.py` 的项目材料读权限、版本和显式操作约定。在现有项目页加入口，证据卡作为现有项目资料的派生视图。
- 本地草稿固定项目 ID、版本、需求文本和原文引用。引用复用材料 ID、内容哈希与逐字摘录。准备卡片时由服务端重新读取来源，核对项目归属、权限和摘录；Agent 返回的相关性和贡献概括仍由开发者确认。
- 生成分享卡时重新核对固定预览和选择。修改需求、摘录、选择或来源版本后重新预览。分享数据由明确允许的字段构成，项目内部标识、本机路径和未勾选正文留在本地。
- 写集限 `mvp/devtools/` 下的证据卡准备逻辑、工作台路由和项目页，以及对应 HTTP／DOM 测试。沿用原项目库。平台账号绑定和真实写入由接收方接口明确后另接。

## 验收与开工顺序

| 验收场景 | 通过条件 |
| --- | --- |
| 完整走一遍 | 一条需求、一个已有项目，至少一项可核对证据。接收者打开卡片即可回答任务、贡献、证据、缺口四个问题。 |
| 降级情况 | 无证据、有材料但贡献待核、来源失效时，界面呈现相应状态，失效来源不能进入新分享卡。 |
| 分享边界 | 两份证据只勾一份，复制及接收者页面只出现勾选内容；改选后旧预览失效。跨项目或与原文不一致的引用被拒绝。 |
| Demo 事实 | 使用一条获准展示的真实需求和一份真实作品。若现阶段只有样例，显式标注样例，真实试点验收保持待办。 |

先定需求和证据卡字段，再做服务准备与接收者页面，最后跑实机演示。工程可先用明确标注的样例并行验证。数据接口和页面由 Maker 实现，独立 Checker 复查核源、分享字段和实际读回。真实需求负责人、获准展示的作品和平台接收目标当前均待锁定。

## 本地接口

三步都使用现有的项目模式和显式 POST。请求共同固定项目当前版本、需求标题、交付物、验收要求、可选编号和样例标记。

| 操作 | 输入与结果 |
| --- | --- |
| `project-evidence-prompt` | 输入最多六份已选材料，返回仅包含这些材料的整理指令。开发者可以手写证据，也可粘贴 Agent 返回的草稿。 |
| `project-evidence-prepare` | 输入最多三条证据、待确认项及逐项分享选择。核对权限与逐字摘录，返回接收者可以看到的字段和绑定本次预览的摘要值。 |
| `project-evidence-share` | 输入同一份草稿、选择和预览摘要值。再核对项目当前版本和每项来源，返回接收者卡片和 Markdown。至少选择一段核对过的摘录，成品链接可作为补充。 |

Agent 草稿先显示为「本人贡献待核」。勾选「我已核对贡献」后才显示为「开发者确认」。材料可读和摘录匹配表示能追溯出处。证据卡的三步操作只读取项目资料并生成预览与文本。
