# 团队职责与入场方式

更新：2026-10-18。沿用产品总纲的职责划分，实际人选、工时、预算与评审节奏尚需按当前投入记录。

## 当前身份与权限

之负责产品方向、取舍与最终体验判断。Codex、Hermes／小禾及其他执行身份协助整理、实现、派工与核验；它们不计作已经到岗的人类工程编制。通道身份、工具凭据与岗位不是同一个概念。

历史文档中的杜／Oracle 参与记录不证明当前投入，不能直接给历史协作者分配新任务。旧协作记录保留历史用途，现行协作按实际负责人认领。

## 现在最需要的职责

| 职责 | 进入时间 | 首个可审查交付 |
|---|---|---|
| 产品／交互负责人 | 现在 | 真实任务、状态／动作表、体验取舍与样机反馈 |
| 核心／集成工程主责 | 现在 | 看懂已合入内核、复用边界、DSH／外部运行契约与真实纵切 |
| 客户端／桌面交互主责 | 起点讨论即加入，样机期主责 | 工作站目标与供给、三态、HUD／工作岛及恢复体验 |
| 独立质量／可靠性主责 | 启动即加入，可兼职 | 先定义证据，再核验输入、持久化、运行与失败路径 |

两类工程主责可由一位复合工程师阶段性承担，但需降低并行量；不能保持两个人的估时。Maker／Checker 对同一候选保持独立。

中期按真实工作量补原生系统／设备集成、用户研究与设计协作；首轮不因长线模型、硬件或社区愿景预设完整部门。

## 新协作者从哪里开始

1. 读根 README、产品总览、交互与开发状态，理解完整目标及当前已完成范围。
2. 选定一个已有路线中的小交付；读相关源码、原方案与测试，提出最小改造和验证。
3. 核对提交、差异、并行工作与独立实施位置；用独立分支，保护原改动。
4. 交代码／文档候选、真实证据、失败与未覆盖项，交独立核验后再请求合并。
5. 更新状态与文件地图，让下一位不必重讲全部历史。

不让新人从重新发明产品定义开始。评估合作者时看他能否解释复用、风险、证据和实际可用时间。

## 之主要做什么

选择首轮真实任务、体验标准、人员资源与范围取舍；亲手过样机，给具体反馈。普通字段、命令和工程实现由主责处理；涉及范围、成本、来源权限与发布时带具体选项。

每周先看实际交付、可试体验、需要决定的事和下一动作。原始日志留工程入口，不要求用户逐项追。
