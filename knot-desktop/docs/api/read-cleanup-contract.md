# 只读观察清理与 Store 关闭

039只修宿主内部只读链，不新增HTTP、Run/执行入口、读授权或Session范围。旧版本/许可/请求指纹校验、同Store读Run、执行器业务结果均保持。

观察器取得handle后仍只调用一次close并等待。真实close异常创建脱敏DSH_CLOSE_FAILED，优先于业务失败及最终abort；关闭成功后的取消仍DSH_READ_CANCELLED。工厂使用模块私有WeakSet标记实际close异常，并提供窄识别谓词；公开code、同公开Error类或跨序列化重建的错误都不能作为资源释放失败证明。原始异常不向外暴露。

绑定在promise拒绝处、pending移除之前记录该cleanup事实。即便失败观察已结束，sticky事实仍保留到binding生命结束。普通read denied/schema/IO失败或干净取消不sticky。dispose先关闭入口、abort在途、撤销service并等待全部观察settle；只有service撤销失败或真实cleanup sticky才拒绝DSH_OBSERVER_DISPOSE_FAILED。重复/并发dispose返回同一Promise，不重试close/unprovide；保留service引用不再接受observe。

插件只在observer owner的dispose成功后关闭Store。storage disposer缓存自己的Promise，失败后重复调用仍拒绝，不能跳过清理屏障自动释放Store锁。service unprovide失败属于scope释放未证，不是普通业务错误；虽然closed fence仍生效，也不能据此宣告完整清理完成。此处保守保留Store，需要明确资源核对，不提供自动修复/强关入口。

audit-enabled scope与storage共用当前owner的缓存disposal，只有resolve才标记released。依赖重绑只允许无owner或旧owner明确released；旧owner pending/failed时拒绝DSH_OBSERVER_OWNER_BUSY，不创建替代binding或用新成功抹旧失败。storage关闭一旦开始则拒绝DSH_OBSERVER_CLOSED，即使旧scope随后成功也不能新bind。已取得binding立即登记owner，后续scope effect等初始化异常仍受其屏障约束；取得前的注册冲突没有新observer资源，可以释放新Store且不替换旧owner。

测试采用实际源模块、临时Store、synthetic persistence/Session故障seam和已有官方库合成只读回归。plugin保锁用专用Node子进程承载其私有测试FileHandle，断言先于子进程退出；父进程仅删除自建临时目录。没有生产锁清理或force-close API。该证据不证明现实OS句柄泄漏、native宿主安全退出、异常后资源已恢复，也不代表正式部署或完整产品验收。
